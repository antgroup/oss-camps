# 2026 蚂蚁开源轻训营 Issue 指南

本仓库提供“2026 蚂蚁开源轻训营 · 高校行”专属 Issue 的设计说明和 GitHub Issue Forms。项目维护者可使用模板发布适合学生认领、边界清晰且能够客观验收的开源任务。

## 时间安排

| 事项                | 时间                            |
| ------------------- | ------------------------------- |
| 项目提交 Issue 截止 | 2026 年 9 月 4 日下班前         |
| 学生认领时间        | 2026 年 9 月 7 日至 10 月 24 日 |

每个项目建议准备 **5 个左右**的 Issue，并在低难度与中高难度之间合理分配。

## 使用模板

仓库提供低难度和中高难度两类 GitHub Issue Form，每类均包含中文和英文版本：

- **低难度任务（[中文](.github/ISSUE_TEMPLATE/camp-low-difficulty.yml) / [English](.github/ISSUE_TEMPLATE/camp-low-difficulty-en.yml)）**：适用于文档完善、部署体验优化、单点改进、示例补充和组件小特性。
- **中高难度任务（[中文](.github/ISSUE_TEMPLATE/camp-medium-high-difficulty.yml) / [English](.github/ISSUE_TEMPLATE/camp-medium-high-difficulty-en.yml)）**：适用于端到端功能、性能优化、模型移植、协议集成和技术方案设计。

将 [`.github/ISSUE_TEMPLATE`](.github/ISSUE_TEMPLATE) 目录复制到目标项目的默认分支后，即可在 GitHub 的“New issue”页面选择对应模板。

使用前，请先在目标项目创建以下标签：

| 标签                 | 用途               |
| -------------------- | ------------------ |
| `蚂蚁开源轻训营专属` | 标识活动专属 Issue |
| `轻训营-低难度`      | 标识低难度任务     |
| `轻训营-中高难度`    | 标识中高难度任务   |

发布时请在预填标题 `【2026 开源轻训营专属 Issue】` 后补充一句话任务描述，例如：

```text
【2026 开源轻训营专属 Issue】补充 Python SDK 快速上手示例
```

使用英文模板时，请在 `[2026 Open Source Camp Exclusive Issue]` 后补充英文任务描述，例如：

```text
[2026 Open Source Camp Exclusive Issue] Add Python SDK quickstart examples
```

## 工程校验

仓库通过 [校验脚本](scripts/validate.rb) 检查 Issue Forms 的 YAML 语法、必需字段、组件类型和字段 ID，同时检查 Markdown 文件末尾换行。提交前请在仓库根目录运行：

```shell
ruby scripts/validate.rb
```

推送到 `main` 分支或提交 Pull Request 时，[GitHub Actions](.github/workflows/validate.yml) 会自动执行相同检查。参与修改前请阅读 [贡献指南](CONTRIBUTING.md)。

## 编写要求

每个 Issue 都应完整说明以下内容：

1. **问题描述**：讲清现状痛点和任务价值，尽量提供数据、日志、截图或对比结果。
2. **期望内容或功能改进**：将目标拆为 3 至 5 项可执行子任务，并给出建议技术路径。
3. **验收标准**：使用可量化、可复现的完成判据，明确环境、输入、预期输出或性能目标。
4. **完成方式与交付物**：明确 PR、Discussion、报告、截图、演示视频等交付形式。
5. **参考资料**：提供相关代码、文档、原始项目或参考实现，降低首次贡献门槛。
6. **认领方式**：保留模板中的活动统一说明，不要修改或删除。

代码类任务统一以 `oss-camp2026` 为目标分支，避免直接影响主分支。项目可根据自身流程从该分支评审、验证并择机合入。

## 难度划分

| 难度     | 典型范围                             | 设计重点                               |
| -------- | ------------------------------------ | -------------------------------------- |
| 低难度   | 文档、小特性、单点修复、快速上手示例 | 一次解决一个具体问题，有清晰参考入口   |
| 中高难度 | 端到端功能、性能优化、移植、复杂集成 | 给出技术边界、基线、环境和硬性验收指标 |

不要继续细分难度。任务应具有真实项目价值，同时能够让具备相关基础的学生在活动周期内独立或组队完成。

## 设计原则

### 开放任务允许并行贡献

模板、示例和生态共建类 Issue 应注明“多人可并行认领不同方向，增量合入，不要求单人完成全部”。同时列出可选方向、登记方式和去重规则，避免重复工作。

### 开放选题必须有交付底线

LLM 应用、集成示例等开放任务可以允许学生自拟方向，但必须约束可运行性和可演示性。例如要求至少一个可交互界面、两个端到端示例、不超过 2 分钟的演示视频，以及说明核心能力的 README。

### 系统与性能任务提供基线

操作系统、数据库、运行时等任务必须说明测试环境、当前数据和对标目标。探索性任务应明确做到“原型”或“逻辑框架”即可，避免学生误解为生产级交付。

### 模型移植强调一致性与构建

模型移植任务应提供原模型和参考实现链接，验收至少覆盖相同输入下的输出一致性，以及指定平台上的构建和运行结果。

### 可选 AI 使用策略报告

项目可要求提交 AI 使用策略报告，建议覆盖：

- 使用了哪些 AI 工具，以及分别用于哪些环节；
- 如何验证 AI 生成的代码、分析或文档；
- 哪些 AI 建议未被采用，以及拒绝的原因。

报告用于考察批判性使用能力，不以使用 AI 的多少作为评价依据。

## 发布前检查

- Issue 数量是否约为 5 个，难度分布是否合理；
- 标题是否具体到单一任务范围；
- 是否使用活动专属标签和正确的难度标签；
- 代码类任务是否指向 `oss-camp2026` 分支；
- 是否包含 3 至 5 项可执行子任务；
- 验收标准是否可量化、可复现；
- 是否提供足够的代码、文档或参考实现入口；
- 并行任务是否说明方向划分和去重方式；
- 是否保留统一认领说明。

更完整的分类建议和参考案例见 [轻训营专属 Issue 模板.md](轻训营专属%20Issue%20模板.md)。
